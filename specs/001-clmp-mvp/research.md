# Research: CLMP MVP — Consultant-to-Placement Lifecycle

**Feature**: `001-clmp-mvp` | **Date**: 2026-10-02 | **Plan**: [plan.md](./plan.md)

The spec has no open `[NEEDS CLARIFICATION]` markers, and the constitution fixes the stack
(React + TypeScript + Vite, Java + Spring Boot, H2). The research below settles the technical
choices the spec leaves open. Each entry gives the decision, why it was chosen, and what else was
considered.

---

## R1. Runtime and framework versions

- **Decision**: Java 21 (LTS), Spring Boot 4.0.x (latest stable patch at implementation time),
  built with Maven via the Maven Wrapper (`./mvnw`). Node.js 22 LTS (20.19+ minimum), React 19,
  TypeScript 5.x, Vite 7, React Router 7 (declarative/library mode).
- **Rationale**: These are current LTS and stable lines. Maven Wrapper means contributors only
  need a JDK installed. Spring Boot 4 targets Java 17+ and supports Java 21. Vite 7 needs
  Node 20.19+.
- **Alternatives considered**: Spring Boot 3.5.x. It is an acceptable fallback if a Boot 4
  starter causes trouble, but it would have to be pinned explicitly. Gradle was rejected because
  Maven is the more common default for Spring Boot teams, and the build has no special needs.
  Next.js and CRA were rejected because the constitution requires Vite.
- **Environment note**: The current WSL shell has no JDK, and Node is v12.22. Both are too old
  or missing. See [quickstart.md](./quickstart.md) for the prerequisites. Acknowledged by
  reviewer (2026-10-02): the environment will be verified before implementation, and the
  versions don't change.

## R2. Backend dependencies (minimal set)

- **Decision**: `spring-boot-starter-web`, `spring-boot-starter-data-jpa`,
  `spring-boot-starter-security`, `spring-boot-starter-validation`, and `com.h2database:h2`
  (runtime). For tests: `spring-boot-starter-test` and `spring-security-test`.
- **Rationale**: Each one maps to a spec need. Web serves the REST API. JPA covers persistence and
  optimistic locking. Security covers sign-in, sessions, and RBAC (FR-001–FR-007). Validation
  provides field-level messages (FR-104).
- **Alternatives considered**: Lombok and MapStruct were rejected because Java records cover DTOs
  and hand-written mappers are small. Flyway/Liquibase are deferred (see R4). Spring Modulith was
  rejected because package conventions plus one ArchUnit-style check are enough (see R12), and
  Modulith would be a new dependency without a current need.

## R3. Frontend dependencies (minimal set)

- **Decision**: `react`, `react-dom`, `react-router` for runtime. For dev and test: `typescript`,
  `vite`, `@vitejs/plugin-react`, `vitest`, `@testing-library/react`,
  `@testing-library/user-event`, `jsdom`. Styling is plain CSS (CSS Modules per component plus
  one global token file). The API client is a small typed wrapper around `fetch`.
- **Rationale**: About eight pages of forms and tables don't justify a UI kit, a state library,
  or a data-fetching library. Shared `DataTable`, `FormField`, `StatusBadge`, `PageLayout`,
  `EmptyState`, and `ErrorBanner` components meet the CLAUDE.md reuse convention.
- **Alternatives considered**: TanStack Query would handle caching and refetching, but a small
  `useApi` hook covers loading/error/empty states for this scope. It can be added later if
  staleness becomes a problem. MUI and Ant Design add a lot of weight and theming overhead.
  React Hook Form isn't needed because the forms are small and validation is authoritative on
  the server.

## R4. Persistence mode and schema management

- **Decision**: H2 in-memory by default (`jdbc:h2:mem:clmp`), with schema generated by Hibernate
  (`ddl-auto=create`) and demo data seeded at startup by a `DemoDataSeeder` (`ApplicationRunner`).
  An opt-in `file` Spring profile switches to `jdbc:h2:file:./data/clmp` with `ddl-auto=update`
  so data survives restarts. The H2 console is enabled only in the `dev` profile, and only ADMIN
  can reach it.
- **Rationale**: The MVP is a demonstrable prototype. A fresh, consistent seed on every start is
  the fastest way to show the lifecycle (SC-001) and makes manual testing repeatable. Seeding in
  Java lets passwords be BCrypt-hashed and keeps referential setup readable.
- **Alternatives considered**: Flyway migrations would add a dependency and migration upkeep
  before any production database exists. They belong in the future PostgreSQL spec (constitution
  III). `data.sql` seeding was rejected because it can't hash passwords cleanly and is brittle
  with generated IDs.

## R5. Authentication and session handling

- **Decision**: Spring Security with server-side `HttpSession` (cookie `JSESSIONID`, HttpOnly,
  SameSite=Lax). Login uses a JSON endpoint `POST /api/auth/login` that authenticates through
  `AuthenticationManager` and saves the `SecurityContext` to the session. The session idle timeout
  is `server.servlet.session.timeout=30m` (FR-006). Passwords are stored with BCrypt. Inactive
  users are refused through `UserDetails.isEnabled()` (FR-005). Every failure returns the same
  generic `401 INVALID_CREDENTIALS` (AS 1.2).
- **CSRF**: Enabled with `CookieCsrfTokenRepository.withHttpOnlyFalse()` and the SPA request
  handler pattern. The frontend reads `XSRF-TOKEN` and sends `X-XSRF-TOKEN` on mutating requests.
- **Unauthenticated API calls** return `401` JSON, not a redirect. The SPA then sends the user to
  `/login` with a "session expired" message.
- **Rationale**: Session cookies are the simplest secure option for a same-origin internal SPA.
  They give a real idle timeout and a clean logout, and no token ever reaches JavaScript.
- **Alternatives considered**: JWT bearer tokens need refresh and revocation logic and leave a
  token where JavaScript can read it. HTTP Basic has no logout or idle timeout. OAuth/SSO is out
  of scope (spec Assumptions).

## R6. Same-origin development topology

- **Decision**: In development the Vite dev server (`:5173`) proxies `/api` to Spring Boot
  (`:8080`), so the browser sees a single origin. No CORS configuration is needed.
- **Rationale**: This avoids CORS and cross-site cookie complications, and CSRF and session
  cookies work unchanged.
- **Alternatives considered**: Enabling CORS on the backend is more configuration and more
  attack surface. Bundling the built SPA into the Spring Boot jar is a reasonable later step but
  isn't needed for the MVP, since deployment concerns are out of scope.

## R7. Authorization model (role + ownership)

- **Decision**: Enforce it in two layers, both on the server:
  1. **Role gate**: `@PreAuthorize("hasAnyRole(...)")` on controller methods, following
     [contracts/authorization-matrix.md](./contracts/authorization-matrix.md).
  2. **Ownership/scope gate**: In the service layer, a per-module `*AccessPolicy` (for example
     `SubmissionAccessPolicy.assertCanUpdate(user, submission)`) resolves the caller's
     `CurrentUser` (user id, role, linked recruiter id). List queries apply scope as a JPA
     `Specification` predicate, so out-of-scope rows never load.
  - A refused action returns `403 FORBIDDEN` with code `NOT_AUTHORIZED` and changes nothing
    (FR-004). Single-record reads outside scope also return `403` rather than `404`, which matches
    the spec's "not authorized" outcome.
  - A RECRUITER user with no linked recruiter profile gets an empty scope: lists come back empty
    and the dashboard shows a message (edge case).
- **Rationale**: Role checks are declarative and easy to audit. Ownership checks need the loaded
  record, so they sit in services, which is where the constitution puts business rules.
- **Alternatives considered**: ACL or permission-evaluator frameworks are overkill for four roles
  and two ownership rules. Frontend-only filtering is forbidden by constitution VII.

## R8. Role-shaped responses (sensitive-field protection)

- **Decision**: Use separate response DTOs per view instead of nulling fields on a shared DTO:
  - `ConsultantListItem` never contains email, phone, visa expiration, or notes (FR-024).
  - `ConsultantDetail` has nested sections. `contact` is present only for permitted viewers
    (FR-103). `submissions`, `placements`, and `marketingAssignment` are omitted for
    HR_OPERATIONS (FR-064).
  - History and activity DTOs carry a `description` rendered for the viewer. For HR_OPERATIONS,
    trigger descriptions that mention a vendor, client, or rate are rendered generically (for
    example "Placement created" instead of "Placement at Acme via Vendor X"). The trigger is
    stored in structured form (event code + entity type/id), so redaction happens at read time and
    nothing is lost.
  - Logging: the request-logging filter (if any) and exception handlers never log request bodies
    for auth endpoints. Domain logs reference ids only, never contact details or rates.
- **Rationale**: If a field isn't on the DTO, it can't leak. Rendering at read time is what lets
  HR see the "Placed" status change without seeing commercial details (Clarification Q2,
  FR-082).
- **Alternatives considered**: Jackson `@JsonView` is less explicit and easy to misconfigure.
  Storing two descriptions per history row duplicates data, and the copies can drift apart.

## R9. Cross-module lifecycle transitions (FR-032, FR-036, FR-072)

- **Decision**: A dedicated `lifecycle` module holds `ConsultantLifecycleService`, the single
  owner of consultant status rules. It works with the consultant, marketing, submission, and
  placement **repositories**, not their services, so there are no service-to-service cycles.
  Workflow services (`MarketingService`, `SubmissionService`, `PlacementService`) call explicit
  lifecycle methods (for example `onSubmissionStatusChanged(submission, old, new, actor)` or
  `onPlacementCreated(placement, actor)`) **within the same `@Transactional` boundary**. Every
  automatic change writes a `HistoryRecord` with `systemTriggered=true`, the triggering user,
  the event code, and the triggering record.
  - Manual consultant status changes (FR-031) also go through `ConsultantLifecycleService`. That
    keeps both transition tables, manual and automatic, in one class with one set of tests.
- **Rationale**: The spec asks for "explicit automatic transitions" (Clarification Q4).
  Synchronous method calls inside one transaction are atomic (FR-072 "as one action"), easy to
  read, and easy to test. A failure anywhere rolls everything back.
- **Alternatives considered**: Spring `ApplicationEvent` listeners hide control flow and make
  atomicity depend on listener phase configuration. A generic state-machine library adds a
  dependency for a few small transition tables. Enum-based transition maps are clearer.

## R10. Concurrency: lost updates and per-consultant invariants

- **Decision**:
  - **Optimistic locking**: `@Version` on Recruiter, Consultant, MarketingAssignment, Submission,
    and Placement. Update/transition requests carry the `version` the client last saw. A mismatch
    returns `409 CONCURRENT_MODIFICATION` with "Record changed — reload" (edge case "Concurrent
    edits").
  - **Per-consultant serialization**: Operations that check a per-consultant invariant first lock
    the consultant row with `PESSIMISTIC_WRITE` (`SELECT … FOR UPDATE`). These are: creating or
    reopening a marketing assignment (FR-042), creating a placement (FR-075), and setting
    Inactive with no open submissions. Two concurrent requests for the same consultant then can't
    both pass the check.
- **Rationale**: H2 can't express a partial unique index ("one open assignment per consultant").
  A row lock on the aggregate root is the simplest correct guard, and the version column handles
  user-visible stale edits.
- **Alternatives considered**: A stored `open_assignment_id` column with a unique constraint
  would denormalize the data and still need upkeep. Application-level synchronized blocks don't
  hold up across transactions.

## R11. Error response format

- **Decision**: RFC 9457 `ProblemDetail` (built into Spring) from a single
  `@RestControllerAdvice`, with extension properties: `code` (stable machine code), `fieldErrors[]`
  (FR-104), `missingItems[]` (FR-035), `duplicates[]` (FR-055), and `existingRecordId` (AS 4.4).
  See [contracts/rest-api.md § Errors](./contracts/rest-api.md#errors).
- **Rationale**: This is a standard shape with no extra dependency, and the frontend can map
  `code` to messages and `fieldErrors` to inline field messages.
- **Alternatives considered**: A custom error envelope would do the same thing without the
  standard.

## R12. Module boundaries inside the monolith

- **Decision**: Use package-per-domain under `com.ensar.clmp`: `auth`, `reference`, `recruiter`,
  `consultant`, `marketing`, `submission`, `placement`, `lifecycle`, `history`, `dashboard`,
  `report`, `common`. Each domain package holds its own `web` (controller + DTOs), `service`, and
  `domain` (entity + repository) subpackages. Allowed dependency direction:
  `web → service → domain`. Cross-domain access goes only through another module's service or
  through `lifecycle`/`history`. Boundaries are enforced by code review plus one plain JUnit test
  that scans imports and checks that no controller references an `@Entity` type in its signatures
  (constitution IV, "never return entities").
- **Rationale**: This gives clear ownership without the overhead of a modules framework.
- **Alternatives considered**: Layer-first packages (`controllers/`, `services/`) scatter each
  domain's code. Gradle/Maven multi-module is premature for one deployable.

## R13. Shared filter definitions (dashboard/report/list consistency, SC-006, FR-083, FR-092)

- **Decision**: Each list has one filter record (for example `SubmissionFilter{statuses,
  recruiterId, vendorId, clientId, submittedFrom, submittedTo}`) that converts to a JPA
  `Specification` combined with the caller's scope predicate. Dashboard counts and report cells
  are computed **by counting through the same filter + scope**, and each count returns the filter
  as query parameters (`link`) that the frontend appends to the list URL. A report total and the
  list it links to then run the same predicate.
- **Rationale**: This makes the consistency the spec requires true by construction, and an
  integration test can check it for each role.
- **Alternatives considered**: Hand-written aggregate SQL per widget is faster to write once but
  drifts from the list filters over time.

## R14. Performance at the stated scale (SC-007)

- **Decision**: Use server-side pagination on all lists (`page`, `size` ≤ 100, default 25; `sort`
  allowlisted per list). Add indexes on `consultant.status`, `consultant.current_recruiter_id`,
  `submission.status`, `submission.recruiter_id`, `submission.consultant_id`,
  `submission.submitted_date`, `submission(consultant_id, vendor_id, client_id,
  job_title_normalized)`, `placement.recruiter_id`, `placement.created_at`,
  `history_record(occurred_at)`, and `history_record(consultant_id)`. Dashboard counts use
  `count` queries. The recruiter performance summary uses grouped counts, never per-row loops.
  Use DTO projections and fetch joins on list queries to avoid N+1 queries.
- **Validation**: A `perf` Spring profile seeds 500 consultants, 50 recruiters, and 2,000
  submissions. A test or manual check confirms that list, dashboard, and report endpoints respond
  in under 2 s locally.
- **Alternatives considered**: Caching isn't needed at this volume and would complicate
  consistency.

## R15. Time and dates

- **Decision**: Timestamps are stored as `Instant` (UTC). Business dates (start, target,
  submitted, placement start) use `LocalDate`. "Today", "current calendar month", and "not in
  the future" are evaluated in a configurable organization zone (`clmp.time-zone`, default
  `America/New_York`) through an injected `java.time.Clock`, so tests can fix the clock.
- **Rationale**: Rules such as overdue, current month, and future dates need one agreed calendar,
  and an injected clock makes the date rules testable.
- **Alternatives considered**: Using the server's default zone gives silently different results
  on different machines.

## R16. Testing strategy (constitution VI)

- **Decision**:
  - **Backend unit tests**: Transition tables in `ConsultantLifecycleService`, marketing and
    submission state machines, the readiness check (FR-035), and duplicate normalization (FR-055).
  - **Backend integration tests** (`@SpringBootTest` + MockMvc + H2, with users seeded per test
    class): one test class per user story's acceptance scenarios. One parameterized
    **authorization matrix test** runs every endpoint × role from
    [contracts/authorization-matrix.md](./contracts/authorization-matrix.md) (SC-002). There is
    also a **consistency test** that compares dashboard and report counts with list totals for
    each role (SC-006), and a sensitive-field test that asserts HR responses contain no
    vendor/client/billRate keys (FR-064).
  - **Frontend** (Vitest + Testing Library): navigation visibility per role, the route guard
    redirecting forbidden routes, the duplicate-warning confirm flow, and field-error rendering
    from `ProblemDetail`.
  - **End-to-end**: manual walkthrough scripted in [quickstart.md](./quickstart.md) (SC-001,
    SC-008). A browser E2E framework is deferred because it would be extra infrastructure without
    a current requirement.
- **Rationale**: Tests target the acceptance criteria directly with minimal infrastructure.
- **Alternatives considered**: Playwright E2E is the best follow-up if manual walkthroughs become
  costly. Testcontainers isn't needed with H2.

## R17. Seed data

- **Decision**: The seeder creates:
  - Users: `admin` (ADMIN), `manager` (MANAGER), `recruiter1` and `recruiter2` (RECRUITER, each
    linked to a recruiter profile), `recruiter3` (RECRUITER, deliberately unlinked, for the empty
    state), `hr` (HR_OPERATIONS), and `inactive.user` (deactivated).
  - Teams: Java, .NET, Data & Analytics, DevOps & Cloud. Regions: East, Central, West, Offshore.
  - Visa types are a code enum (FR-021 fixed list).
  - About 12 consultants spread across every status, a few vendors and clients, and submissions
    across statuses so the dashboard and reports aren't empty.
  - Demo passwords are documented in the quickstart and apply only to the `dev` profile. The
    seeder refuses to run if the `prod` profile is active.
- **Rationale**: This covers every role and edge case needed for the independent tests in each
  user story.
- **Alternatives considered**: Starting with an empty database would make SC-001 ("using only
  seeded reference data") and the dashboard checks slower to demonstrate.

## R18. Spec inconsistencies found during planning (surfaced per constitution VIII)

1. **US6 narrative vs. FR-017/FR-070 — RESOLVED (2026-10-02)**: The US6 narrative said "the
   recruiter or a manager converts it into a placement", but Clarification Q3, FR-017, and FR-070
   say MANAGER cannot create placements. The spec narrative has been corrected to "the
   submission's recruiter or an Admin", noting that Managers view placements organization-wide
   but cannot create or edit them. The plan already followed the FRs (ADMIN or the owning
   RECRUITER only), so no design change was needed.
2. **Recruiter Assignment entity**: The spec lists it as a key entity. The plan represents it as
   the current FK `consultant.current_recruiter_id` plus immutable `HistoryRecord` rows of
   change type `RECRUITER_ASSIGNMENT`. That gives "over time" history without a second source of
   truth. It isn't a behavioral deviation. **Accepted by reviewer (2026-10-02).**
3. **"Needs reassignment" flag**: This is derived as "current recruiter is Inactive" instead of
   being stored. It is set by deactivation and cleared by reassignment, as the spec requires. If
   an Admin reactivates the recruiter, the flag also clears, which seems correct, but the spec
   doesn't say so. **Assumption — accepted by reviewer (2026-10-02); no persisted flag.**
4. **Submissions for a consultant on Hold**: The spec leaves open submissions "as is" when a
   consultant goes on Hold. The plan allows their status to keep changing (no consultant
   auto-transition happens on interview changes, because those rules only fire from
   Ready/Marketing/Interviewing). Creating new submissions is still refused (FR-052).
   **Assumption — accepted by reviewer (2026-10-02).** Extended by R19-4: a Hold consultant may
   still be placed from an existing Offer submission.
5. **Consultant creation minimum**: FR-020 lists the editable fields, and FR-035 implies some
   (phone, skill, experience, visa) may be missing while the consultant is on Bench. The plan
   requires only first name, last name, and email at creation. Everything else is optional until
   the consultant is marked Ready. **Assumption — accepted by reviewer (2026-10-02).**
6. **Local toolchain (see R1 environment note)**: **Acknowledged by reviewer (2026-10-02).** The
   design stays on Java 21 and Node 22. The active shell environment will be verified before
   implementation starts, and the architecture doesn't change.

## R19. Analysis remediation decisions (2026-10-02)

These decisions came from the `/speckit-analyze` review and are recorded in the spec
(Clarifications § analysis remediation), the contracts, data-model.md, and tasks.md. None changes
MVP scope.

1. **Vertical slices**: The Foundational phase now holds only what US1 consumes. Every other shared
   backend or UI piece (history, reference API, paging, version guard, org clock, list and form
   components) is built in the first story that uses it (constitution II).
2. **Consultant detail panels**: The detail page renders the Marketing, Submissions, Placements,
   and on-Hold open-submission panels for non-HR viewers. HR_OPERATIONS never sees them
   (FR-025, FR-064).
3. **Placement ownership**: ADMIN may create a placement from any OFFER submission. A RECRUITER
   may create one only when they are `submission.recruiter_id`. The placement's recruiter is
   always the submission's recruiter, so the creating recruiter can always view their placement
   under FR-073. ADMIN and MANAGER keep organization-wide visibility.
4. **Hold → Placed**: A consultant on HOLD may be placed from an existing OFFER submission. The
   placement moves them HOLD → PLACED and closes the open marketing assignment ("Placed"). New
   submissions stay blocked while on HOLD.
5. **Unlinked recruiter**: Lists show a shared "contact an Admin" empty state instead of a silent
   empty list.
6. **Interviews scheduled (Vendor/Client Activity)**: Counted as submissions currently in
   INTERVIEW_SCHEDULED whose `submitted_date` is in the selected range, so the figure is
   reproducible with `status=INTERVIEW_SCHEDULED` plus `submittedFrom/submittedTo` on the
   submission list (FR-092). This replaces the earlier history-based definition.
7. **No submission edit**: `PUT /api/submissions/{id}` is removed. Submissions support create,
   status progression, and notes only.
8. **Marketing creation**: Allowed only for READY consultants (FR-040).
9. **Placement edit dates**: An edited start date must be ≥ the source submission's submitted date.
10. **Delivery order**: The plan's slices now follow the spec and task order (US2 consultants
    before US3 recruiters).
