# Data Model: CLMP MVP

**Feature**: `001-clmp-mvp` | **Date**: 2026-10-02 | **Plan**: [plan.md](./plan.md) |
**Research**: [research.md](./research.md)

The model is persisted in H2 through JPA (schema generated by Hibernate, see research R4). Every
mutable aggregate has an optimistic-lock `version` (R10). Nothing is hard-deleted (FR-028,
Assumptions). All timestamps are UTC `Instant`s. All business dates are `LocalDate` evaluated in the
organization time zone (R15).

## Entity Overview

```text
AppUser 1───0..1 Recruiter ──*─ Team / Region (reference)
                     │ 1
                     │ current primary recruiter
                     * 
                 Consultant 1──* MarketingAssignment 1──* MarketingNote
                     │ 1
                     *
                 Submission *──1 Vendor
                     │      *──1 Client
                     │ 1          1──* SubmissionNote
                     │            1──* SubmissionDuplicateRef ──> Submission (earlier)
                     0..1
                 Placement

HistoryRecord  (immutable; references any of the above by entity_type + entity_id)
```

## AppUser (`app_user`)

| Field | Type | Rules |
|-------|------|-------|
| id | Long | PK |
| username | String(60) | Required, unique (case-insensitive) |
| password_hash | String(100) | BCrypt; **never serialized, never logged** (FR-007) |
| display_name | String(120) | Required |
| role | enum `Role` | Exactly one of `ADMIN, MANAGER, RECRUITER, HR_OPERATIONS` (FR-002) |
| active | boolean | `false` → sign-in refused (FR-005) |

Users are seeded. There are no user-administration screens (Assumptions).

## Recruiter (`recruiter`)

| Field | Type | Rules |
|-------|------|-------|
| id | Long | PK |
| full_name | String(120) | Required |
| email | String(254) | Required, valid email, **unique** case-insensitive (FR-010) |
| phone | String(30) | Optional |
| team_id | FK → team | Required, must reference active team (FR-011) |
| region_id | FK → region | Required, must reference active region (FR-011) |
| status | enum `RecruiterStatus` | `ACTIVE` (default) / `INACTIVE` |
| user_id | FK → app_user, nullable | **Unique**; target user role MUST be `RECRUITER` (FR-015) |
| version, created_at, updated_at | | |

**Derived**: `assignedConsultantCount` = count of consultants where
`current_recruiter_id = recruiter.id` (FR-012). This is computed by a grouped count query and never
stored.

**Rules**:
- Deactivating a recruiter with `assignedConsultantCount > 0` requires `confirm=true`. Without
  it, the API returns `409 CONFIRMATION_REQUIRED` with `affectedConsultantCount` (FR-014).
  Deactivation never alters existing marketing assignments or submissions (edge case).
- Every status change writes a HistoryRecord (`entity_type=RECRUITER`).

## Consultant (`consultant`)

| Field | Type | Rules |
|-------|------|-------|
| id | Long | PK |
| first_name, last_name | String(60) | Required at creation |
| email | String(254) | Required at creation, valid email, **unique** case-insensitive (AS 2.5) |
| phone | String(30) | Optional at creation; required for Ready (FR-035) |
| city, state | String(80) / String(40) | Optional |
| primary_skill | String(80) | Optional at creation; required for Ready |
| additional_skills | String(500) | Optional, comma-separated free text |
| years_experience | Integer | 0–50 when present; required for Ready |
| visa_type | enum `VisaType` | Optional at creation; required for Ready |
| visa_expiration_date | LocalDate | Optional |
| notes | String(2000) | Optional |
| status | enum `ConsultantStatus` | Initial `BENCH` (FR-022) |
| current_recruiter_id | FK → recruiter, nullable | At most one at a time (FR-033) |
| version, created_at, created_by_user_id, updated_at | | |

**Explicitly not stored** (FR-027): SSN, date of birth, bank details, identity document images.

**Derived**:
- `needsReassignment` = `current_recruiter_id IS NOT NULL AND recruiter.status = INACTIVE`
  (research R18-3).
- `missingReadinessItems` = which of {firstName, lastName, email, phone, primarySkill,
  yearsExperience, visaType, active assigned recruiter} are missing (FR-035).

**Sensitive fields** (FR-024, FR-103): `email`, `phone`, `visa_expiration_date`, and `notes`
appear only in the detail view, and only for ADMIN, MANAGER, HR_OPERATIONS, and the currently
assigned RECRUITER.

**Recruiter assignment** (FR-033, FR-034): A change sets `current_recruiter_id`. The target
recruiter must be `ACTIVE`. Each change writes a HistoryRecord (`change_type=RECRUITER_ASSIGNMENT`,
old and new recruiter names). If the consultant has an open marketing assignment, its owner
recruiter and team transfer to the new recruiter in the same transaction, with a history row on
the assignment (edge case "reassigned mid-marketing"). Existing submissions keep their
`recruiter_id`.

### ConsultantStatus state machine

`BENCH, READY, MARKETING, INTERVIEWING, PLACED, ACTIVE_PROJECT, HOLD, INACTIVE` (FR-030)

**Manual transitions** (ADMIN, HR_OPERATIONS only — FR-031):

| From | To | Guard |
|------|----|-------|
| BENCH | READY | FR-035 complete; else `422 READINESS_INCOMPLETE` + `missingItems` |
| READY | BENCH | — |
| PLACED | ACTIVE_PROJECT | today ≥ placement.start_date |
| ACTIVE_PROJECT | BENCH | — (project ended) |
| BENCH, READY, MARKETING, INTERVIEWING | HOLD | reason required; **cascade**: Active marketing → HOLD |
| HOLD | BENCH | — |
| HOLD | READY | FR-035 complete |
| any (≠ INACTIVE) | INACTIVE | reason required; refused if any open submission (status ∉ {REJECTED, WITHDRAWN, PLACED}) → `422 OPEN_SUBMISSIONS_EXIST`; **cascade**: open marketing → CLOSED reason "Consultant inactive" |
| INACTIVE | BENCH | — |

MARKETING, INTERVIEWING, and PLACED can **never** be set manually (FR-032).

**Automatic transitions** (`ConsultantLifecycleService`, same transaction as the trigger, FR-032,
FR-036):

| Trigger event (`TriggerEvent`) | Consultant from | Consultant to |
|--------------------------------|-----------------|---------------|
| `MARKETING_ACTIVATED`, `MARKETING_REOPENED` | READY | MARKETING (no change if MARKETING/INTERVIEWING) |
| `MARKETING_CLOSED` (reason ≠ Placed) | MARKETING | READY (no change if INTERVIEWING) |
| `SUBMISSION_INTERVIEW_SCHEDULED` | READY, MARKETING | INTERVIEWING (no change if already) |
| `SUBMISSION_LEFT_INTERVIEW_STAGES` — the consultant no longer has any submission in INTERVIEW_SCHEDULED / INTERVIEW_CLEARED / OFFER | INTERVIEWING | MARKETING if an ACTIVE marketing assignment exists, else READY |
| `PLACEMENT_CREATED` | READY, MARKETING, INTERVIEWING, HOLD | PLACED |
| `CONSULTANT_HOLD` (cascade to marketing) | — | marketing ACTIVE → HOLD |
| `CONSULTANT_INACTIVE` (cascade to marketing) | — | marketing DRAFT/ACTIVE/HOLD → CLOSED ("Consultant inactive") |
| `PLACEMENT_CREATED` (cascade to marketing) | — | marketing DRAFT/ACTIVE/HOLD → CLOSED ("Placed") |

## MarketingAssignment (`marketing_assignment`)

| Field | Type | Rules |
|-------|------|-------|
| id | Long | PK |
| consultant_id | FK → consultant | Required |
| owner_recruiter_id | FK → recruiter | Defaults to consultant's current recruiter (FR-040) |
| owner_team_id | FK → team | Derived from owner recruiter at create/transfer |
| start_date | LocalDate | Required |
| target_date | LocalDate | Required; ≥ start_date (FR-043) |
| status | enum `MarketingStatus` | Initial `DRAFT` |
| hold_reason | String(500) | Set on → HOLD |
| close_reason | String(500) | Set on → CLOSED; system values `"Placed"`, `"Consultant inactive"` |
| closed_at | Instant | |
| version, created_at, created_by_user_id | | |

**Derived**: `overdue` = `status ≠ CLOSED AND target_date < today` (FR-043).

**Invariant** (FR-042): at most one assignment with status ∈ {DRAFT, ACTIVE, HOLD} per
consultant. This is enforced in the service under a consultant row lock (R10). A violation returns
`409 OPEN_ASSIGNMENT_EXISTS` with `existingRecordId` (AS 4.4).

**Creation guard**: the consultant MUST be READY at creation (FR-040), else
`422 CONSULTANT_NOT_ELIGIBLE`. Activation also requires READY (AS 4.1–4.3).

### MarketingStatus state machine (FR-041)

| From | To | Actors | Guard / effect |
|------|----|--------|----------------|
| DRAFT | ACTIVE | ADMIN, owning RECRUITER | consultant READY → consultant MARKETING |
| DRAFT | CLOSED | ADMIN, owning RECRUITER, MANAGER | reason optional |
| ACTIVE | HOLD | ADMIN, owning RECRUITER, MANAGER | reason required; consultant status unchanged |
| HOLD | ACTIVE | ADMIN, owning RECRUITER, MANAGER | consultant ∈ {READY, MARKETING, INTERVIEWING}; READY → MARKETING |
| ACTIVE, HOLD | CLOSED | ADMIN, owning RECRUITER, MANAGER | reason required; consultant MARKETING → READY |
| CLOSED | ACTIVE | ADMIN, MANAGER | consultant READY; close_reason ≠ "Placed"; FR-042 holds; READY → MARKETING |

"Owning RECRUITER" means the RECRUITER user linked to the consultant's **current** recruiter
(FR-040, AS 4.7). MANAGER can never create assignments or edit dates and notes (FR-017).

## Submission (`submission`)

| Field | Type | Rules |
|-------|------|-------|
| id | Long | PK |
| consultant_id | FK → consultant | Required; consultant ∈ {READY, MARKETING, INTERVIEWING} at creation (FR-052) |
| recruiter_id | FK → recruiter | Defaults to consultant's current recruiter; kept for reporting credit after reassignment |
| vendor_id | FK → vendor | Required (find-or-create by name, FR-051) |
| client_id | FK → client | Required (find-or-create by name) |
| job_title | String(120) | Required, trimmed |
| job_title_normalized | String(120) | lower + trim + collapse whitespace (duplicate check) |
| submitted_date | LocalDate | Null while DRAFT; required once ≥ SUBMITTED; defaults to today on → SUBMITTED; never in the future (FR-054) |
| bill_rate | Decimal(10,2) | Required, > 0, USD/hour (FR-053) |
| status | enum `SubmissionStatus` | Initial `DRAFT` or `SUBMITTED` (AS 5.1) |
| duplicate_acknowledged | boolean | `true` when created despite duplicates (FR-055) |
| duplicate_acknowledged_by_user_id / _at | FK / Instant | Recorded on confirm |
| version, created_at, created_by_user_id | | |

**Indexes**: `status`, `recruiter_id`, `consultant_id`, `submitted_date`, and
`(consultant_id, vendor_id, client_id, job_title_normalized)` for duplicate lookup.

### SubmissionDuplicateRef (`submission_duplicate_ref`)

| Field | Type | Rules |
|-------|------|-------|
| submission_id | FK → submission | The new (acknowledged) submission |
| earlier_submission_id | FK → submission | Each matched earlier submission |

**Duplicate rule** (FR-055, edge case): an earlier submission matches when it has the same
consultant, same vendor id, same client id, and the same `job_title_normalized`, in **any** status
including WITHDRAWN and REJECTED.

### SubmissionStatus state machine (FR-056–FR-058)

`DRAFT, SUBMITTED, UNDER_REVIEW, INTERVIEW_SCHEDULED, INTERVIEW_CLEARED, REJECTED, OFFER, PLACED, WITHDRAWN`

| From | Allowed to |
|------|------------|
| DRAFT | SUBMITTED, WITHDRAWN |
| SUBMITTED | UNDER_REVIEW, INTERVIEW_SCHEDULED, REJECTED, WITHDRAWN |
| UNDER_REVIEW | INTERVIEW_SCHEDULED, REJECTED, WITHDRAWN |
| INTERVIEW_SCHEDULED | INTERVIEW_CLEARED, REJECTED, WITHDRAWN |
| INTERVIEW_CLEARED | INTERVIEW_SCHEDULED, OFFER, REJECTED, WITHDRAWN |
| OFFER | REJECTED, WITHDRAWN (PLACED only via placement creation) |
| REJECTED, WITHDRAWN, PLACED | — (terminal, FR-057) |

**Groupings** used by the dashboard and reports:
- *Active* = {SUBMITTED, UNDER_REVIEW, INTERVIEW_SCHEDULED, INTERVIEW_CLEARED, OFFER} (FR-080)
- *Interview stage* = {INTERVIEW_SCHEDULED, INTERVIEW_CLEARED}
- *Interview/offer stage* (lifecycle) = {INTERVIEW_SCHEDULED, INTERVIEW_CLEARED, OFFER}
- *Open* = all except {REJECTED, WITHDRAWN, PLACED}

**Side effects**: → INTERVIEW_SCHEDULED fires `SUBMISSION_INTERVIEW_SCHEDULED`. Any change that
leaves the consultant with no submission in an interview/offer stage fires
`SUBMISSION_LEFT_INTERVIEW_STAGES`.

**Actors**: ADMIN, or a RECRUITER where `submission.recruiter_id = me` OR the consultant's current
recruiter is me (FR-063). MANAGER is read-only (FR-017).

## Placement (`placement`)

| Field | Type | Rules |
|-------|------|-------|
| id | Long | PK |
| submission_id | FK → submission | Required, **unique**; submission MUST be OFFER (FR-070) |
| consultant_id, recruiter_id, vendor_id, client_id | FK | Copied from submission |
| job_title | String(120) | Copied from submission |
| start_date | LocalDate | Required; ≥ submission.submitted_date (edge case "Dates") |
| bill_rate | Decimal(10,2) | Required, > 0; pre-filled from submission, editable |
| contract_term_months | Integer | Required, whole number 1–60 (FR-071) |
| created_at, created_by_user_id, version | | |

**Derived**: `expectedEndDate` = `start_date.plusMonths(contract_term_months)` (FR-071).

**Guards**: The consultant must not be PLACED or ACTIVE_PROJECT (FR-075, "two offers"). This is
checked under the consultant row lock. A consultant on HOLD may be placed from an existing OFFER
submission. The creator must be ADMIN, or the RECRUITER who is `submission.recruiter_id`
(FR-070). `recruiter_id` is always copied from the submission.

**Creation effect** (FR-072, one transaction): placement saved → submission OFFER → PLACED →
consultant (READY/MARKETING/INTERVIEWING/HOLD) → PLACED → open marketing → CLOSED ("Placed"). Each step writes a HistoryRecord with
the trigger set to this placement. The response lists the consultant's other open submissions
(FR-076).

**Edits** (ADMIN only, FR-074): start_date, bill_rate, contract_term_months. An edited start_date
must be ≥ the source submission's submitted_date (400 otherwise). Each edited field writes a
HistoryRecord (`change_type=FIELD_EDIT`).

There is **no placement status** in the MVP (Assumptions).

## HistoryRecord (`history_record`) — immutable

| Field | Type | Notes |
|-------|------|-------|
| id | Long | PK |
| entity_type | enum `HistoryEntityType` | `CONSULTANT, RECRUITER, MARKETING_ASSIGNMENT, SUBMISSION, PLACEMENT` |
| entity_id | Long | Id of the changed record |
| consultant_id | Long, nullable | Denormalized for scope filtering of activity (FR-102) |
| owner_recruiter_id | Long, nullable | Submission/placement recruiter at time of change (recruiter "own" scope) |
| change_type | enum `ChangeType` | `CREATED, STATUS, RECRUITER_ASSIGNMENT, OWNER_TRANSFER, PROFILE_UPDATED, FIELD_EDIT, NOTE_ADDED` |
| field_name | String(60), nullable | For FIELD_EDIT, or the list of changed field names for PROFILE_UPDATED |
| old_value / new_value | String(255), nullable | Status codes or display values; **never** passwords, and never consultant email/phone/visa expiration/notes values (PROFILE_UPDATED records field *names* only) |
| reason | String(500), nullable | Hold/close/inactive reason |
| note | String(2000), nullable | Optional note on a submission status change (FR-059) |
| actor_user_id | Long | The user whose action caused the change (also for automatic changes) |
| actor_display_name | String(120) | Snapshot, so history reads without joins |
| occurred_at | Instant | Server time |
| system_triggered | boolean | `true` for FR-032 automatic changes |
| trigger_event | enum `TriggerEvent`, nullable | Set when `system_triggered` |
| trigger_entity_type / trigger_entity_id | enum / Long, nullable | The triggering record (e.g., the submission or placement) |

**Rules**:
- There is no update or delete path anywhere (FR-101). The repository only exposes `save` for new
  rows and query methods.
- `description` is **rendered at read time** for the viewer (research R8). For HR_OPERATIONS,
  descriptions of triggers from submissions or placements omit vendor, client, and rates, and
  only CONSULTANT-entity rows are returned at all.
- Activity feed (FR-102) = latest 20 rows visible to the viewer:
  - ADMIN, MANAGER: all.
  - RECRUITER: rows where `consultant_id` ∈ my current consultants OR `owner_recruiter_id` = me.
  - HR_OPERATIONS: `entity_type = CONSULTANT` only.
- Indexes: `(entity_type, entity_id, occurred_at)`, `(occurred_at)`, `(consultant_id)`.

## Validation Summary (FR-104)

Bean Validation on request DTOs produces `400 VALIDATION_FAILED` with `fieldErrors[]`. Business
rule refusals use the codes in [contracts/rest-api.md § Errors](./contracts/rest-api.md#errors). A
refused request never partially persists, because each service method is one transaction.
