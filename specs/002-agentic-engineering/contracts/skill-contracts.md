# Contract: CLMP Skills

**Feature**: `002-agentic-engineering` · Sources: [research](../research.md) R3, R4, R8–R10

Each skill is a single `SKILL.md` under `.claude/skills/`. Both the model and the user can invoke
it. It has `metadata.owner: clmp` and no `allowed-tools`, and it links to the governing documents
rather than copying them.

## CLMP skills vs Spec Kit skills

| | `speckit-*` (10) | `clmp-*` (2) |
|---|---|---|
| Owner | Generated by Spec Kit 1.0.13, tracked in `.specify/integrations/claude.manifest.json` | The CLMP project, reviewed like code |
| Answers | *What* to build and in what order (spec → plan → tasks → implement) | *How* to build, judge, and validate a change in this codebase |
| Content | A generic process | CLMP architecture, roles, lifecycle, tests, and environment |
| Edit policy | Never edit them; upgrade through `specify` | Edit through a reviewed change |

## `clmp-change-workflow`

**Description (draft)**: "CLMP project rule (not a Spec Kit step): how to make a change in this
codebase. Use when implementing, fixing, or modifying CLMP backend or frontend code, including
during /speckit-implement tasks."

**Steps**:

1. **Scope**: find the approved spec and task. If there is none, the change is either a trivial
   fix (say so) or needs `/speckit-specify` first.
2. **Impact**: for anything beyond one file, delegate to `clmp-codebase-analyst`.
3. **Architecture rules**, each with its anchor in the code:
   - Controller → Service → Repository. Business rules live in services.
   - Request/response DTOs. Entities are never exposed (`architecture/NoEntityInControllerSignatureTest`).
   - Role gates use `@PreAuthorize` and `SecurityConfig`. Ownership checks live in the service
     `*AccessPolicy` / `*Specifications` classes, per
     `specs/001-clmp-mvp/contracts/authorization-matrix.md`.
   - Frontend `permissions.ts` is UX only.
   - Consultant status changes go only through `lifecycle/ConsultantLifecycleService`. Automatic
     transitions record the actor and trigger in history.
   - No sensitive values in logs or list DTOs. History stores field names only
     (`security/SensitiveFieldExposureTest`).
   - Errors use `ErrorCode` + `ProblemDetail`. Edits use optimistic versioning (`VersionGuard`).
4. **Vertical slice**: UI → API → service → persistence, as the task needs. Reuse the shared
   components, and handle the loading, empty, validation, and error states.
5. **Tests**: write tests for each affected acceptance criterion: backend `*Test` / `*IT` on
   `IntegrationTestBase`, frontend Vitest in `frontend/src/test/`.
6. **Stay in scope**: no unrelated refactors, dependencies, or infrastructure.
7. **Hand off**: `clmp-code-reviewer`, then the fixes, then `clmp-release-readiness`.
8. **Report** deviations, assumptions, and blockers (constitution VIII).

## `clmp-release-readiness`

**Description (draft)**: "CLMP project rule (not a Spec Kit step): decide whether a change is
ready to merge. Use when asked to validate, test, check readiness, or confirm Quality Gates for a
CLMP change."

**Steps**:

1. Delegate the checks to `clmp-test-validator`. The main agent does not choose or run them
   itself.
2. **Check selection** (the single source of these rules):

   | Changed area | Checks |
   |--------------|--------|
   | `backend/**` | `cd backend && ./mvnw test -Dtest=<Class>` (targeted), then `cd backend && ./mvnw verify` |
   | Authorization/ownership or sensitive-data code | also `-Dtest=AuthorizationMatrixTest,SensitiveFieldExposureTest` |
   | `frontend/**` | `cd frontend && npm run typecheck`, `npm test -- --run`, `npm run build` |
   | Docs/specs/`.claude/` only | not run: no code change (unless full/all is requested) |
   | Explicitly asked for **full** / **all** validation | every backend and frontend check above (targeted where applicable, `verify`, the authorization tests, typecheck, tests, build), regardless of changed paths; perf still only if asked |
   | Performance | only if asked: `./mvnw verify -Dgroups=perf` |

3. **Environment blockers**:
   - Java is not 21, or Node is below 20.19 → name the tool; install nothing.
   - The output contains `Timeout waiting for worker to respond` and the path starts with `/mnt/`
     → an environment blocker. Say that the frontend tests were not exercised, and give the
     workarounds: clone into the WSL file system, or use Windows-native Node.
4. **Quality Gates**: map the results to each constitution gate:

   | Gate | Evidence |
   |------|----------|
   | Builds | backend `verify` and frontend `build` |
   | Tests | targeted and full test results |
   | Acceptance criteria | the impact report requirements, plus the review "Checked" section |
   | No role bypass or data exposure | reviewer findings, plus the authorization tests where selected |
   | Deviations documented | reviewer scope deviations, plus the change description |

5. **Verdict**: `ready`, `not ready`, or `blocked by environment`. An environment blocker is never
   reported as `ready`.
