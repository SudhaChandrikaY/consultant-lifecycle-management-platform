# Contract: CLMP Skills

**Feature**: `002-agentic-engineering` · Sources: [research](../research.md) R5, R6, R13, R15

Both skills live in `.claude/skills/`, use `metadata.owner: clmp`, set no `allowed-tools`, and can
be invoked by both the model and the user. They link to governing documents instead of copying
them.

## How they differ from Spec Kit skills

| | `speckit-*` (10) | `clmp-*` (2) |
|---|---|---|
| Owner | Generated by Spec Kit 1.0.13, hash-tracked in `.specify/integrations/claude.manifest.json` | CLMP project, reviewed like code |
| Answers | *What* to build and in what order (spec → plan → tasks → implement) | *How* to build, judge, and validate a change in this codebase |
| Content | Generic, project-agnostic process | CLMP architecture, roles, lifecycle, tests, environment |
| Edit policy | Never edit; upgrade through `specify` | Edit through a reviewed change |

## `clmp-change-workflow`

**Description (draft)**: "CLMP project rule (not a Spec Kit step): how to make a change in this
codebase. Use when implementing, fixing, or modifying CLMP backend or frontend code, including
while running /speckit-implement tasks."

**Steps (in order)**:

1. **Confirm scope**: find the approved spec and task (`.specify/feature.json`, `specs/*/tasks.md`).
   If there is none, it is either a trivial fix (constitution I, say so) or stop and recommend
   `/speckit-specify`.
2. **Analyze impact**: for anything beyond one file, delegate to `clmp-codebase-analyst` and keep
   its report.
3. **Respect the architecture** (`references/architecture-rules.md`):
   - Controller → Service → Repository. Business rules live in services only.
   - Request/response DTOs at the API boundary. Never return or accept entities; the
     `NoEntityInControllerSignatureTest` architecture test enforces this.
   - Role gates on controllers (`@PreAuthorize`) **and** ownership checks in services, per
     `specs/001-clmp-mvp/contracts/authorization-matrix.md`. The frontend `permissions.ts` is UX
     only.
   - Consultant status changes go only through `ConsultantLifecycleService`. Automatic transitions
     record the actor and the trigger in history, in the same transaction.
   - No sensitive values in logs or list DTOs. History records field *names*, not values.
   - Optimistic versioning on edits; errors use `ErrorCode` and `ProblemDetail`.
4. **Build the vertical slice**: UI → API → service → persistence, as the task needs. Reuse the
   shared frontend components (`DataTable`, `FormField`, `ErrorBanner`, status badges, etc.).
   Handle the loading, empty, validation, and error states.
5. **Test**: add or update tests for each affected acceptance criterion. Backend: `*Test` (unit)
   and `*IT` (integration, `IntegrationTestBase`, fixed clock). Frontend: Vitest under
   `frontend/src/test/`.
6. **Stay in scope**: no unrelated refactors, dependencies, or infrastructure (constitution V).
7. **Hand off**: request `clmp-code-reviewer`, fix the findings, then run `clmp-release-readiness`
   (which delegates to `clmp-test-validator`).
8. **Report**: deviations, assumptions, and blockers in the change description (constitution
   VIII).

## `clmp-release-readiness`

**Description (draft)**: "CLMP project rule (not a Spec Kit step): decide whether a change is
ready to merge. Use when asked to validate, test, check readiness, or confirm Quality Gates for a
CLMP change."

**Steps**:

1. Delegate execution to `clmp-test-validator` (independence). The main session doesn't select or
   run the checks itself.
2. Use `references/check-selection.md` (the single source of the rules below).
3. Map the results to **every** constitution Quality Gate:

   | Quality Gate | Evidence |
   |--------------|----------|
   | Frontend and backend builds pass | Validator: `backend verify`, `frontend build` (or a justified skip) |
   | Tests for affected workflows pass | Validator: targeted and full results |
   | Acceptance criteria satisfied | Impact report requirement list + review "Checked" |
   | No role check bypassed, no sensitive data exposed | Reviewer findings (constitution VII) + authorization tests when selected |
   | Deviations documented | Reviewer scope deviations + the change description |

4. Report `ready`, `not ready`, or `blocked by environment`. An environment blocker is never
   reported as `ready`.

### `references/check-selection.md` (rules)

| Changed paths | Checks |
|---------------|--------|
| `backend/**` | targeted: `./backend/mvnw -q -f backend/pom.xml test -Dtest=<Class>[,<Class>]`; full: `./backend/mvnw -f backend/pom.xml verify` |
| `frontend/**` | `npm --prefix frontend run typecheck`; `npm --prefix frontend test -- --run`; `npm --prefix frontend run build` |
| Touches `*AccessPolicy*`, `*Specifications*`, `SecurityConfig`, `@PreAuthorize`, `permissions.ts`, DTOs, logging, or the seeder | additionally `-Dtest=AuthorizationMatrixTest,SensitiveFieldExposureTest` |
| List, dashboard, report queries or indexes | perf: `./backend/mvnw -f backend/pom.xml verify -Dgroups=perf` (otherwise `not run` with a reason) |
| Docs/specs/`.claude/` only | no build checks; report `not run: no code change` |

Targeted tests run first, so failures show up fast. The full backend verify always runs for a
backend change.

### `references/environment-blockers.md`

- Toolchain: `java -version` must report 21; `node -v` must report ≥ 20.19. If not, it is an
  environment blocker naming the tool. Never install anything.
- WSL `/mnt/` + Vitest `Timeout waiting for worker to respond`: an environment blocker. The
  frontend tests were **not exercised**. Workarounds: clone into the WSL file system, or run with
  Windows-native Node (README "WSL note").
- Port or network failures in integration tests that don't depend on code: an environment
  blocker, re-run once.
